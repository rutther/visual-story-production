# 搜索、参考评价与匹配

> 阶段规则：本章中的编码、MP4、成片检查均以当前交付范围和用户授权为前提。Web预览阶段不要求生成视频；先完成可编辑工程的实际检查。历史案例中的数量、参数和角色不是新项目默认值。

## 1. 搜索之前写出问题

“高级”“炫酷”“优雅”是目标感受，不是可直接执行的检索条件。将它转成具体问题：

- 照片如何保留主体，同时容纳标题和字幕？
- 时间变化如何在手机画面上看清？
- 主体换阵营如何让观众理解是同一个人？
- 地图放大后标签怎样保持稳定？
- 信息很多时如何决定显示次序？

问题越具体，参考越容易被比较和验证。

## 2. 分开搜索视觉、机制和技术

视觉搜索：同用途、同设备、近似内容密度的实际作品。机构作品集、设计社区、栏目包装、出版物、公开视频均可，但要进入作品页面实际看画面。

机制搜索：信息如何被组织和解释，例如时间线、关系图、对比、分解、地图定位、操作演示。关键词用任务和对象，而不仅是品牌。

技术搜索：具体实现和约束，例如SVG缩放标签、确定性时间轴、图片缓存、字幕换行、Canvas导出。优先官方文档、维护者仓库和最小可复现例子。

三者不能互相代替。GitHub星数不能证明设计适合，漂亮截图不能证明运行流畅，品牌名也不能证明该机构确实使用某版式。

## 3. 搜索渠道的用法

| 渠道 | 适合找什么 | 需要核对 |
|---|---|---|
| 工作室/机构官网 | 原作、作者、视觉系统 | 真实作品名、日期、职责 |
| GitHub | 实现、示例、工具 | 许可证、维护状态、依赖、安全和实际运行 |
| Hugging Face | 模型、演示、媒体能力 | 输入输出、硬件、成本、限制、是否适合当前任务 |
| X/设计社区 | 最新案例、过程、技巧 | 作者原帖、完整视频、是否搬运、实际用途 |
| YouTube/公开视频 | 连续节奏、转场、演示 | 动作前后状态、时间、字号、声音、实际画幅 |
| 图形新闻部门 | 地图、数据叙事、解释方法 | 数据定义、图形语义、移动端结构 |

不安装不可信代码来“看效果”。下载参考和运行依赖按环境授权执行。私有素材不要为了搜索效果自动上传外部演示。

## 4. 查询的组成

用`对象 + 信息任务 + 媒介/设备 + 技术或风格限定`组合关键词。例如：

- `editorial portrait video animated timeline mobile`
- `SVG map zoom labels constant screen size`
- `motion design relationship switching diagram`
- `product assembly animation exploded view reference`

中文概念可转成常用专业英文检索，再把结果对应回当前需求。检索没有强结果时，改一个维度而非成批猜URL。搜到有用案例后深入验证，不以更多查询数量当进展。

## 5. 参考评价卡

每个被采用的参考记录：

`来源/作者/作品 → 实际看到的状态 → 解决的问题 → 借鉴部分 → 不适用部分 → 当前实现 → 验证方式`

评价维度：

- 骨架：主信息在哪里，谁压在谁上面，照片占多少。
- 可读性：目标设备是否读得到，中文能否承载。
- 动作语义：运动解释了什么，是否只是装饰。
- 内容适配：当前素材能否实现，是否依赖没有的视频/三维/音乐。
- 技术成本：能否导出，能否稳定运行，是否需联网或付费。
- 风格一致性：是否符合用户已确认的世界。

判断写具体理由，不编主观总分。一次采用少数强参考，分别承担构图、照片、图形或动作的职责，避免拼贴多个品牌的标志性装饰。

## 6. 从参考到实现的翻译

先提取关系和规则，再落为参数。比如“文字主导、图片内缩”翻译为区域比例和字号阶梯；“动作清晰”翻译为一个焦点、明确起止和可读停留；“精准”翻译为对齐、时间函数和端点检查。

若两套方案只改色彩、颗粒、字体，骨架和信息任务相同，它们并不是有意义的构图备选。要比较就改变照片规模、文字位置、信息主次、明暗关系或动作结构，并用同一真实内容渲染。

## 7. 保存研究结论的边界

只把实际核对过、能重复使用的原则进入通用方法。收藏链接不是验证。某个作品中的好看选择可能只适用于该内容，不要把单个案例上升为所有视频必须遵守的规则。
